- B-PLAYER: `Component.getString` has no intermediary row (it comes from brigadier's `Message`), so displayName goes through an adapter. (R-EXP-21)
- B-WORLD, B-PLAYER: several members resolve only through interface rows (1.8.9 `BlockView` blockState and `CommandSource.getPos` position; modern `EntityAccess#getBoundingBox`), lowered as INVOKEINTERFACE. (R-EXP-22)

## Deviations from the docs (with reason)
- Adapters ship in `com.blanket.adapters.<set>` (lowering §5.2 vs §4.5). (D-061)
- `features.json` is read directly, with no generated `types/Blanket.json` (binding-format §6, example 10). (D-061)
- Key code tables are Java in each set's `KeyCodes` adapter, with no `types/Key.json` (api-surface §3.9). (D-061)
- `KeyBinding.register` is bound, but its per-loader registration recipe is M3 (events-and-hooks §4.7, S-07). (D-061)
- Stub bodies throw `AssertionError("blanket stub")` per api-surface §1 rule 5 (M1 code threw UnsupportedOperationException). (D-061)
- `Screen` ships without `add`/`remove` until widgets (M6). (D-061)
- C10 baseline is the T1 jar, since no release exists (D-060). (D-061)
- Remapped adapters stay in `blanket-bindings/build/adapters/` in M2, because a bindings-jar package would make a Gradle task cycle. (D-061)
- M1-verify finding 5 (`lookup` cannot resolve `loader:` references) is deferred to M3, where native events grow. (D-061)
- REMAP: the plan's five test classes are one `RemapTest` (9 cases). `Collisions` covers §4.8 member collisions only, not class-name collisions.
- FOLD: `Reachability.check` has an overload taking a feature-range function.
- B-KEYS: `KeyBinding.register` queues in runtime `KeyQueue`; draining it into the game is the M3 loader recipe. (D-061)
- B-KEYS: the 26.1.2 category translation key may be `key.category.<modid>.<category>` (open; check on a 26.1.2 launch in M3).
- CHK: C4/C6 judge the per-target adapter closure; built adapters no rule reaches are warnings.
- CORETEST: `blanket-core` tests depend on `:blanket-bindings:remapAdapters`.
